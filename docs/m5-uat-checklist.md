## 现场执行顺序与放行条件

> 前置：由有权限的运维在**目标内网服务器**按 [部署手册](./deployment-guide.md) 准备 Docker Engine 24+、Compose v2、持久化磁盘、内网访问地址与生产环境变量。由团队负责人提供真实团队/PM 信息并创建钉钉机器人。所有测试用例只对**独立测试库**运行，绝不在生产库开启 `HORUS_DEMO_MODE` 或运行验收脚本。

### 1. T5.1 内网部署与网络

- [ ] 将仓库代码部署到内网宿主机；从 `.env.example` 创建未跟踪的 `.env`，更换两个数据库密码，配置 `APP_URL` 为同事可访问的地址，确认 `HORUS_DEMO_MODE=false`。不要公开 3306；仅按需暴露应用端口。
- [ ] 从宿主机执行 `curl -I https://oapi.dingtalk.com`；确认目标服务器可出站访问钉钉（受出口代理/防火墙影响时由运维检查）。
- [ ] 执行 `docker compose up -d --build && docker compose ps`；两个服务均健康。执行 `curl -fsS http://127.0.0.1:${HORUS_PORT:-3000}/api/health`，应返回 `{"ok":true}`。失败时执行 `docker compose logs --tail 100 horus mysql` 排查；**不继续初始化业务数据**。
- [ ] 从另一台内网电脑及手机实际打开 `APP_URL`，匿名访问跳到 `/login` 且没有演示账号入口；如使用反向代理，确认 HTTPS/Host/Origin 一致，写接口无同源校验误拦截。

### 2. T5.2 钉钉机器人联调

- [ ] 在真实内部群创建自定义机器人，设置关键词 `Horus` 或加签密钥；负责人在「通知设置」录入 Webhook、可选密钥、内网可访问的工作台链接并保存。仅在后台页面操作，不在终端/文档打印密钥。
- [ ] 点击「立即发送测试」，群里**实际收到**摘要，标题、内容、链接正确，链接从群成员设备可打开；在页面检查推送日志。测试消息不占每日定时名额。
- [ ] 开启每日异常摘要并确认时区为北京时间、时间符合业务要求；次日实际到达配置时间后，确认仅发出一次且异常项准确。失败时检查日志及次日合并，不把测试发送当作定时验收。

### 3. T5.3 真实团队与成员初始化

- [ ] 负责人用配置的初始账号首次登录并设置强密码；数据库中无演示团队/需求。
- [ ] 创建实际 3～5 个团队，配置名称/简介/颜色和各团队阶段模板；检查左侧导航和团队页面生效。
- [ ] 预建不超过 3 个 PM 并绑定对应团队；本人首次设密登录。确认 PM 看不到未绑定团队的写权限；只用测试账号验证停用/重置密码后旧会话立即失效。

### 4. T5.4 首批需求与上线签收

- [ ] PM 录入首批真实在途需求，检查归属团队、负责人、阶段、优先级与预期上线日期；抽样验证推进、卡点、上线后手动归档。
- [ ] 负责人在桌面和手机核对首页全部未归档需求展示、团队分组与移动端只读；本周新建、卡点、逾期（含高优逾期）高亮可筛选；手机无横向滚动。
- [ ] 打开「需求统计」，切换周/月、团队筛选，核对新建/上线/取消/卡点与周期明细。
- [ ] 执行一次 [手册 §9.2](./deployment-guide.md#92-备份与恢复) 的 MySQL 备份并检查文件非空；把备份复制到公司规定的备份位置。恢复演练仅在隔离库完成。
- [ ] 记录实际内网 URL、完成日期、值班人和签收人（不要记录凭据）；只有 T5.1～T5.4 全部通过且负责人确认，才将状态改为「正式上线」。

## 未满足时的处理

任何健康检查、登录、钉钉实收、业务数据核对或备份失败，均**暂停上线**，保留日志与现有数据，不要删除生产 MySQL 卷。按 [部署手册 §9.4](./deployment-guide.md#94-升级与回滚) 的备份/回滚步骤处理。测试环境中先完成 `npm run db:push`、`npm run db:init`、`npm run test:digest`，以演示模式运行应用后执行 `npm run test:acceptance`（需 Playwright Chromium）；测试通过也不能替代以上现场签收。
